# 2026-08-05 (fourth entry) — CODA's fold lands, is worth 0.8 %, and the denominator was wrong again

## What was implemented

CODA (arXiv 2605.19269) observes that a LayerNorm's affine acts on the *input axis* of
whatever GEMM consumes it, so

    LN(x) W^T + b  =  (gamma . x_hat + beta) W^T + b  =  x_hat (W . gamma)^T + (b + W beta)

Both halves fold into the next matmul at pack time, exactly, and cost nothing at run
time. `FusedEncoder._fold_norm` does it for `norm1 -> in_proj` and `norm2 -> linear1`,
writes ones and zeros into the slab's affine slots so a path that still applies the
affine stays *correct* rather than wrong, and `layernorm<AFFINE>` in the kernel drops
the multiply, the add and two `LDG` for the body's sixteen call sites per board.

⚠️ **The bias uses `W` before gamma is folded in**, because beta is added after the
elementwise gamma. Doing it the other way scales beta by gamma twice, which is wrong by
an amount that looks like a quantisation artefact. `tests/test_model.py` compares
against torch and passes 11/11, which is what makes that claim checkable.

`norm_f` in `tail_epilogue` keeps its affine: the three heads have no bias vector to
fold beta into, and it runs once per board against the body's sixteen.

## What it is worth

The fp8-vs-fp16 ratio `speed.py` reports is **blind to this change** — folding speeds
up both precisions, so the ratio barely moves (1.214x before, 1.220x after) while both
absolutes improve. Measuring it needed the precision held fixed and the fold varied,
which meant a temporary `set_fold` switch and a fourth kernel instantiation.

Paired, order-balanced, six rounds, B = 4096, one process, run twice:

| | unfolded | folded | |
|---|---|---|---|
| fp8 | 80.8k / 80.2k | 81.5k / 80.8k | **+0.82 % / +0.73 %** |
| fp16 | 66.1k / 65.5k | 66.4k / 65.7k | +0.42 % / +0.22 % |

Prior space, `t7h-fp8-002206`, 2041 non-terminal positions: fp8 max |dp| **1.81e-2 ->
1.64e-2**, p95 1.221e-3 unchanged, top-1 moved 1.32 % -> 1.37 %. Folding gamma into
`w_ff1` moves every 128-output block's amax and so changes the fp8 quantisation; the
worry was justified and the measurement says it costs nothing.

## The prediction was 4-6 % and the answer is 0.8 %

`cuobjdump -sass` on `encoder_kernel<true>` says **4056 -> 3888 instructions, −4.1 %**,
FFMA 261 -> 165. Stage 3 had just established that this kernel is issue-limited, so
−4.1 % of instructions should have been about −4 % of runtime. It is −0.8 %.

⚠️ **Static instruction share is not dynamic instruction share.** Each instruction
appears once in the binary; how often it *runs* depends on which loop it sits in. The
two folded LayerNorms run once per layer. The FFN chunk loop inside the same layer runs
**four** times, and its body is the largest block in the kernel. So the LayerNorm is a
much smaller fraction of executed instructions than of compiled ones, and −168 static
is worth roughly −1 % dynamic, not −4 %.

That is the **third** wrong denominator in three attempts:

| attempt | denominator used | what it predicted | what happened |
|---|---|---|---|
| Stage 3, FFN handoff | per-CTA elapsed cycles | 11.3 % | 0.0 % |
| Stage 3, after diagnosis | static instructions | small loss | small loss ✓ |
| CODA fold | static instructions | 4.1 % | 0.8 % |

Elapsed cycles overstate because a stalled CTA hands its SM to its co-resident twin.
Static counts overstate because they ignore trip counts. The denominator that does not
lie is **dynamic instructions**, and the last section measures it — 60,720 per warp —
along with the reason even that one only gets within a factor of two.

## Kept, and why

+0.8 % is small, but it is reproducible, exact, free at run time, costs no accuracy,
and is verified against torch. It also removes the affine from the inner loop, which is
a precondition for anything further in the LayerNorm.

The `set_fold` switch that made the measurement possible is **not** kept: a global flag
that has to agree with how the host packed its weights is a foot-gun with no assertion
available, and `set_fold(false)` against folded weights is silently wrong output. The
A/B script is `scratchpad/foldab.py`; reproducing it means reverting this commit's
kernel hunk.

## What was measured and deliberately not taken

Deferring `1/sigma` into the fp8 descale — CODA's other move, and free on the consumer
side because `gemm_fp8_row` already multiplies by a per-row scale — is worth a further
**−88 static instructions** (3888 -> 3800). It applies only to `ln2`, since `ln1` feeds
the fp16 qkv projection which has no descale to hide it in, and it needs `rstd` to
cross from the LayerNorm's row ownership (warp w owns rows w, w+8, w+16, w+24) to
`quantise_row`'s (warp w owns rows 4w..4w+4) through the row padding. At the observed
static-to-real ratio that is worth about 0.2 %, for a cross-warp handoff and a second
LayerNorm variant. Not taken.

Deferring `mu` as a rank-1 correction is a **loss** here and the arithmetic is simple:
it removes one operation per *input* element (256 per row) and adds one per *output*
element (768 for qkv, 1024 for ff1). CODA's motivation is HBM traffic from materialising
intermediates; this kernel has none, so that trade runs the wrong way.

## Where 90k stands, and what is actually binding

82.2k -> about 82.8k. 90k needs 1.095x and this is 1.008x.

Three attempts have now removed, respectively, 11.3 % of elapsed cycles, 4.1 % of
static instructions, and both together, for a combined 0.8 %. That pattern was itself
the clue, and `ncu` — which **is** installed, at `/usr/local/cuda-12/bin/ncu`, contrary
to what I assumed — settles it. `encoder_kernel<true>`, 512 CTAs, fp8:

    gpu__dram_throughput          0.50 %
    lts__t_sector_hit_rate       99.81 %
    lts__throughput              48.69 %
    l1tex__throughput            63.85 %
    sm__throughput               65.31 %
    smsp__inst_executed     248,705,024  =  60,720 per warp

⚠️ **Nothing is saturated, so the kernel is latency-bound.** DRAM is idle at 0.5 % and
L2 hits 99.8 % of everything, which kills the weight-traffic hypothesis outright — the
12.6 MB slab is L2-resident and L2 is running at half its peak. The SM sits at 65 %.

That explains all three results at once. In a kernel at 65 % of issue peak, deleting
work returns **less than proportionally**, because the time was never the work — it was
waiting. It also explains the two earlier surprises: `__launch_bounds__(THREADS, 1)`
made things 2 % worse rather than better (8 warps instead of 16 is less latency to hide
with), and `gemm_fp8_row`'s ping-pong prefetch cost 27 % (latency-bound *and*
register-starved is the worst combination — buying latency hiding with registers buys
spilling instead).

And the dynamic count is the denominator all three attempts were missing: **60,720
instructions per warp**, against 3,888 static. The fold removes ~56 instructions at each
of two sites that run 8 times, so 896 of 60,720 = **1.5 % dynamic** — against the 4.1 %
static reading, and against 0.8 % measured. Predicted-from-dynamic is within a factor of
two of measured; predicted-from-static was out by five.

## What that makes the next move

Warps per SM = 65536 / (32 x registers per thread). At 128 registers that is 16, and 128
is not negotiable while the mma fragment working set is what it is — Stage 1 established
that. So the levers are, in order of what the profile supports:

1. **Shorten dependency chains** rather than delete work. The LayerNorm reduction is a
   five-step shuffle tree whose result every subsequent instruction waits on; the FFN
   handoff is store-barrier-load-barrier. Latency, not instructions.
2. **Cut registers to reach 3 CTAs/SM**, which needs 85 registers per thread against
   today's 128. That is a large cut and probably out of reach, but it is the only thing
   that raises 16 warps to 24.
3. Stop looking for arithmetic to delete. Three attempts, 0.8 %.

The right next measurement is `ncu --set full` for the stall-reason breakdown
(`smsp__average_warps_issue_stalled_*`), which names *which* latency. That is one run
and it should come before any more kernel edits.
